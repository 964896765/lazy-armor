- V6.0 作为本轮移动端唯一 UI 设计基准；文档中的产品边界用于约束实现，但不替代服务端权威合同和用户本轮授权。
- 独立工作区位于 `C:\la\lazy-armor-mobile-ui-v6`，不混入 `fix/github-webhook-gate`，也不覆盖原工作区的未提交内容。
- 原工作区显示为修改的 8 个移动端文件经 blob、`git diff` 与 `git diff --cached` 复核，内容与 `HEAD` 一致，属于 stat/mtime 状态差异；没有需要复制或 cherry-pick 的未提交移动端代码。
- 当前移动端仍使用左侧 `ConnectionRail` 和 Tabs，首页、计划、记录、审批等页面存在可复用的数据访问与展示组件，但整体导航和信息架构不符合 V6.0。
- 后端已具备 Plan、Execution、Approval、Notification、Scenario Contract V2、FactDemand、SourceResolver、Plan Offer、Availability/Replan 和 17 步投影的主要接口。移动端应复用这些能力，不建立第二套状态或执行引擎。
- 当前没有可信的统一首页投影、统一待办投影、统一搜索接口、计划创建草稿合同和正式在线 AI 能力。缺口补齐前只能显示真实限制、人工步骤或不可用状态，禁止使用 fixture 或客户端推断冒充真实能力。

## 必须整改的问题

### UI-1 全局外壳与首页

- 删除固定左侧 Rail 和传统底部 Tab，改为固定顶部五入口：头像、首页、计划、私密、商城。
- 新增底部三个全局入口：消息、默认搜索且显式切换 AI、待办。
- 首页上区只展示服务端确认符合资格的最多 3 个“正在进行”计划；状态不得由 React Native 自行归并。
- 首页下区展示四大空间与 19 领域场景树，领域和场景创建入口必须携带正式场景上下文。
- 当前 `domains/[domain]` 的静态“AI 建议”和无条件“可创建”不得沿用为真实能力。

### UI-2 计划与执行记录

- 计划中心只保留“全部计划”和“执行记录”两个主栏目，不设置第三个草稿栏。
- 列表筛选、管理状态、下一步、管理对象摘要、来源新鲜度和需要关注状态应来自服务端只读投影。
- 计划详情首屏按“当前情况”和“下一步”组织，渐进展示外层 17 步；内层 15 步只在单次执行诊断中显示。
- `execution-presenter` 当前会将未知状态默认映射为“处理中”，且未完整覆盖 `PENDING_CONFIRMATION`，需要改为穷尽且保守的映射。

### UI-3 五阶段创建与草稿

- 当前 `create.tsx` 不是正式五阶段向导，并且自然语言 fallback 使用 `FixtureAgentModel`，不得作为在线 AI 能力呈现。
- 创建流程必须依次使用场景合同、管理对象、FactDemand/SourceResolver、持久化 Offer 和 Offer choose，最终生成不可变 PlanVersion。
- 草稿必须防抖保存、离页保存、可恢复；只保存白名单字段。恢复时必须复验合同版本和 hash、Offer TTL、授权、新鲜度与治理状态。
- 草稿不是正式 Plan，也不能通过前端字段直接声明来源已授权、事实已验证或计划可执行。

### UI-4 待办与消息

- 统一待办应聚合审批、确认、异常和核实，但每项写操作继续调用对应的权威 Approval、Reconciliation 或业务接口。
- 消息中心只表达事件告知，支持服务端已有的已读与归档；已读不等于待办完成。
- 审批详情必须展示服务端提供的风险、期限、版本、来源与可验证结果，不能由移动端补造。

### UI-5 搜索与万事问 AI

- 默认模式是用户权限范围内的搜索，不自动调用模型，也不检索未解锁或未授权的私密内容。
- 只有用户显式切换“万事问”后才进入 AI 模式；正式模型不可用时明确显示不可用或演示边界。
- AI 可以澄清目标、解释来源缺口和生成计划草稿，但不得宣称事实已验证、动作已执行或结果已完成。

## 后端契约缺口

1. **首页只读投影**：需要 `managementState`、当前情况、下一步、来源健康与新鲜度、Consumer Outcome、待办引用、活动时间、卡片资格和排序依据。
2. **用户场景目录批量投影**：需要四空间映射、场景 key/revision/hash、治理状态、V2-only 状态、用户 readiness、不能创建的原因与正确行动路径，避免 N+1 查询和静态“可创建”。
3. **计划列表与详情只读模型**：需要服务端管理分组、脱敏对象摘要、下一步、Availability、来源新鲜度和 attention；列表支持服务端分页与筛选。
4. **CreationDraft 合同**：需要用户隔离、版本化、字段白名单、阶段、更新时间、场景合同标识、Offer 与过期信息，以及恢复复验规则。
5. **Todo 聚合投影**：需要 `APPROVAL / CONFIRMATION / EXCEPTION / VERIFICATION` 类型、状态、权威对象、计划版本、风险、期限、下一步和详情路由。
6. **Message 投影**：需要类别、关联计划与对象的脱敏摘要、deep link 或 action reference；保留现有 read/archive 命令。
7. **统一搜索接口**：需要用户隔离、分组结果、游标、权限与私密排除、脱敏摘要；默认搜索不得触发模型。
8. **AI 能力与调用合同**：明确 `fixture / online / unavailable`、允许上下文和敏感排除；客户端必须阻断 fixture 冒充在线能力。
9. **共享运行时校验**：新 DTO 应提供共享 schema；不能仅依赖 `api<T>()` 的 TypeScript 强制转换。

## 分阶段实施顺序

- UI-1：全局外壳、顶部五入口、底部三入口、真实“正在进行”卡片和四空间场景树。
- UI-2：计划中心、计划详情、执行记录与服务端四态和 17 步投影。
- UI-3：五阶段创建向导、草稿保存与恢复、Offer 复验。
- UI-4：统一待办与消息中心，保持审批和核实权威接口。
- UI-5：默认搜索与显式 AI 模式，在正式能力不足时保留准确限制。

每阶段独立提交，先运行共享合同构建、移动端测试和类型检查；无法取得 Android、真实 Provider 或同 SHA CI 证据时保持对应外部验收状态未完成。
